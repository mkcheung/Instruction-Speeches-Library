1.2 The migration gap — found, and fixed

This was breaking the product’s central feature

The app container was running current code against a database whose newest migration was dated 18 August. 39 migration files existed on disk; only 30 had been applied.

The symptom was not subtle. AnnotationController reads $review->reviewer->anonymized_at — a column added by one of the unapplied migrations. So every request by a speaker to read their coach’s commentary returned HTTP 500: 

MissingAttributeException: The attribute [anonymized_at] either does not
exist or was not retrieved for model [App\Models\User].
  at app/Http/Controllers/Api/AnnotationController.php:68

These nine migrations were pending and have now been applied:

All nine applied cleanly (pure CREATE TABLE / ADD COLUMN / CREATE INDEX — additive, no data loss). The failing request was then re-run and returned HTTP 200 with the coach’s three published notes. A database dump was taken beforehand and is preserved in this session’s scratchpad.

Why your login failed

You were on http://localhost:5173. The backend is pinned to a single origin — CORS_ALLOWED_ORIGINS=https://app.speechcoach.test, SANCTUM_STATEFUL_DOMAINS=app.speechcoach.test, SESSION_DOMAIN=.speechcoach.test. A request from localhost:5173 comes back stamped with the app.speechcoach.test allow-origin header, the browser sees a mismatch and blocks it, and the fetch rejects with no parseable body. The SPA’s error helper falls through to its generic message because there is no {message, errors} payload to read. Nothing is wrong with your credentials.

2.2 Cold start, in order

Idle memory for the full ten-container stack is about 1.4 GB. 

# 0. From the repo root
cd /Users/marscheung/SideProjects/Instruction-Speeches-Library

# 1. Rebuild. api/ is BAKED into the image — there is no bind mount,
#    so code on disk is invisible to the container until you do this.
docker compose build app queue-worker scheduler web

# 2. Infrastructure first. clamav is slow on a cold signature volume
#    (start_period is 180s) and everything else waits on it.
docker compose up -d postgres valkey seaweedfs mailpit clamav

# 3. Then the application tier
docker compose up -d app web queue-worker scheduler ffmpeg-worker

# 4. Confirm health before going further
docker compose ps

# 5. Migrate. Already done for you, but harmless to re-run.
docker compose exec app php artisan migrate --force

# 6. Seed roles and reserved usernames (idempotent)
docker compose exec app php artisan db:seed --force

#    Demo accounts — only needed if you ever wipe the database
# docker compose exec app php artisan db:seed --class=E2ESeeder --force

# 7. Storage bucket + CORS rules (idempotent; worth re-running —
#    your bucket policy predates the Content-Range header additions)
docker compose exec app php artisan media:initialize

# 8. THE FRONTEND — separate terminal, leave it running.
#    Vite is deliberately never containerized.
cd web && npm run dev

# 9. Open this, and nothing else:
#    https://app.speechcoach.test
Picking this up later? Start with these three checks

The stack was left running and fully working on 30 September 2026 — 10 of 11 services healthy, all migrations applied, Vite on :5173. But containers stop when Docker Desktop restarts, and Vite dies when you close its terminal or reboot. So before assuming anything is broken: 

# 1. Are the containers up? If not, run steps 2-3 above.
docker compose ps

# 2. Is Vite up? If not: cd web && npm run dev
lsof -i :5173

# 3. Any migrations pending? Should print nothing.
docker compose exec app php artisan migrate:status | grep -i pending

If all three pass, go straight to §3 and log in. The only container not doing useful work is whisper-worker, and nothing in the core flow needs it.

Do not test with these

Six real accounts exist from earlier manual testing — ids 1, 2, 3, 29, 41 and 44, including mars.kwong.cheung@gmail.com. None of them has any role assigned.

That is by design, not corruption: registration deliberately assigns no role, and the frontend comments say outright that roles: [] is the normal case for every real user. But it has one consequence that will confuse you — the reviewer directory only lists users holding member or coach, so a role-less account is invisible there and nobody can invite it to review anything.

If you want one of your own accounts to behave like a coach:

Note this command replaces the user’s role set rather than adding to it, and refuses to proceed if it would leave the system without an administrator.

4How the product works

The design you originally set out, confirmed against the code that was actually built.

A speech is private by default. The only thing that grants anyone else access to it is an invitation — and an invitation is not a separate object, it is a row in the reviews table.

4.1 The access model

There is no visibility flag on a speech. There are no shares, no links, no public pool. A reviewer can reach a speech if and only if a reviews row exists naming them, it has not been revoked, and its status is one of three access-granting values: 

ACCESS_GRANTING = [ 'accepted', 'in_progress', 'published' ]

That single rule produces three tiers of what a person sees:

WhoWhat they get back
OwnerEverything — the full payload and a signed playback URL.
Invited, not yet acceptedTitle, duration and the speaker’s name only. No playback URL — they cannot watch until they accept.
Everyone else404, never 403. The system refuses to confirm the speech exists.
Two deliberate absences worth knowing

There is no endpoint that lists speeches available to review. This is intentional — with no open pool, the reviewer directory is the only discovery mechanism, which is why it was built as a real searchable feature rather than a list. And an administrator cannot accept an invitation; that is refused categorically, not merely unauthorized.

4.2 The invitation loop

  1. The speaker invites by name They open their speech, search the reviewer directory, pick a person, write them a message, and send. A reviews row is created with status invited. Re-inviting someone who declined reuses the same row rather than failing; inviting yourself is refused outright.
  2. The reviewer accepts The invitation appears in their dashboard. Accepting moves the row to accepted — and only now does the playback URL become available to them.
  3. The reviewer writes The first annotation flips the row to in_progress automatically.
  4. The reviewer publishes Status becomes published and the drafts become visible to the speaker — all at once.

The reviewer may also decline or abandon; the speaker may withdraw, revoke, or revoke-and-purge.

4.3 The draft / publish rule — verified

Drafts are never visible to the client. This was proven, not assumed.

During this review the loop was driven over HTTP against the live app:

ActionResult
Coach creates a note at t=5s201 Created
Speaker reads the coach’s track while it is a draft200 — 0 notes
Coach presses Publish200
Speaker reads the same track again200 — 1 note

4.4 The four kinds of commentary

KindPublish ruleNotes
Timed text note Draft until the review is published; all drafts publish together The core feature. Timestamp stamps itself on your first keystroke — there is no button. Capped at 200 per review, each up to 120 s long.
Voice note Same rows, same publish action Recorded in the browser. Requires the coach role — this is the only thing the coach role actually gates — plus a verified email. Audio up to 16 MB.
Essay Its own separate Publish Long-form rich text under the player. Publishing is one-way — the button disables afterwards. Before publication the speaker sees an honest empty state, not an error.
Captions / transcript No draft lifecycle at all Not reviewer commentary — these belong to the speech. Only the owner may edit them. Currently non-functional (§10).

4.5 Coach vs. member — a correction worth noting

“Coach” gates far less than you might expect

A plain member can be invited to review, can accept, can write timed notes, can write the essay, and can publish. The coach role gates voice annotations only.

This is deliberate — the original design called for the peer-review path (member reviewing member) to be a first-class case, precisely so that a stray role check would not silently break it. Worth remembering when you test: if you want to prove peer review works, invite member@e2e.test as a reviewer of someone else’s speech.

The walkthrough

  1. Log in as the coach Go to https://app.speechcoach.test/login and sign in as coach@e2e.test / password. Behind it: GET /sanctum/csrf-cookie then POST /login.
  2. Open your review dashboard Navigate to /dashboard. You should see your reviews in four sections, oldest invitations first. Behind it: GET /api/reviews.
  3. Go to the speech — by typing the URL Enter https://app.speechcoach.test/speeches/17 directly.
    Known gap — the dashboard is a dead end

    The dashboard renders no link to the speech. There is no anchor, no button, no row click — the speech id is present in the API payload but never rendered as a link. You must type the URL by hand. This is a real missing feature, not a configuration problem.

  4. Watch the video Press play. The video should stream and scrub normally. Behind it: GET /api/speeches/17, then GET /api/speeches/17/assets/19/playback-url which returns a presigned SeaweedFS URL. Verified: this returns 206 Partial Content, video/mp4, 19,356,216 bytes.
  5. Type a note at a timestamp Pause somewhere and start typing in the notes panel. The timestamp stamps itself on your first keystroke — there is no “add note” button to press first. Nudge the time backward and forward in half-second steps using the arrow controls beside the timestamp, and set how long the note should stay on screen. Behind it: POST /api/speeches/17/annotations.
  6. Watch the live preview Your draft appears over the video with a dashed border marking it provisional — the same overlay component the speaker will eventually see.
  7. Add two more, then delete one Deleting raises a six-second Undo toast. Press it; the note returns.
  8. Write the essay Switch to the Essay tab and write a few paragraphs. It autosaves as you type. Behind it: PUT /api/speeches/17/essay. Note the essay has its own separate Publish button — publishing your notes does not publish the essay.
  9. Publish Press Publish in the notes panel. It reports a count. Behind it: POST /api/reviews/2/publish. Verified: a coach can keep adding and re-publishing notes after an initial publish — the review stays writable.

Optional — prove reviewer isolation

Log in as coach-b@e2e.test and try to reach the other coach’s work on speech 17. Verified: the API returns 403, and nothing anywhere reveals that the other review exists.

What will not work in this script

Voice notes will record and upload, but the transcript will fail — the Whisper model file is absent (§10). The audio itself still plays back. Captions will not generate for the same reason.

9Roles & capabilities

Produced by executing the authorization gates per role against real fixture rows — not by reading the policy files and inferring.

There are no “permissions” in this system

The permission tables exist but are completely empty, and nothing in the codebase ever references a permission. Authorization is roles plus policies, nothing else. Drop “permissions” as a concept when reasoning about this app.

9.2 Three findings worth knowing

1. super_admin is nearly inert in the API

Roles here are mutually exclusive — granting super_admin replaces admin rather than adding to it, and there is no hierarchy. Almost every policy checks for admin specifically, so the super-admin account passes very few of them. Its one real power is entering the admin portal. For moderation testing, use admin@e2e.test, not the super-admin account.

2. Blocking someone does not restrict their access

The block feature governs connection requests only. A blocked user can still be invited as a reviewer, and still reads any speech they already hold a grant on. Connections never widen or narrow what anyone can see — they route a viewer to a profile page, nothing more.

3. An administrator cannot review

Admins are blocked from accepting, declining, withdrawing or abandoning a review, from writing any commentary, and from appearing in or browsing the reviewer directory. They can read anyone’s commentary and revoke reviews. This is intentional — moderation and participation are kept apart.

9.3 Becoming a coach

Two paths, both ending in the same role assignment:

The product path

/become-a-coach → submit an application → attach up to two certification PDFs (magic-byte checked, ClamAV-scanned) → an admin approves it in the portal, which grants the role and writes an audit entry. Rejected applicants may reapply.

The direct path

php artisan user:grant-role {email} coach — instant, and what the seeded coaches use. Use this for testing; the application flow is worth exercising separately but is slower.

One gap found: the admin portal has no UI to grant a role, only to revoke coach status. Promotion to admin or super-admin is artisan-only.

10Known broken edges

What will visibly fail, so you can tell a genuine bug from a known gap.

10.1 Will not work today

Captions and voice transcription — the model file is missing

The whisper-models volume is empty. The worker starts and idles happily, but every captions job fails because there is no model to load. Nothing in the database has a transcript — the transcript table has zero rows.

To fix it (downloads ~142 MiB):

docker compose --profile whisper-model-init run --rm whisper-model-init

Note that transcription is genuinely slow — it reserves 2 CPUs and 4 GB and pegs them for minutes per job. For a quick functional test you can simply skip captions; nothing else depends on them.

The reviewer dashboard does not link to the speech

After accepting an invitation, a coach has no way to click through to the speech — the dashboard renders no link, button or clickable row anywhere. The speech id is present in the API response but never rendered. Workaround: type /speeches/{id} by hand. This is the single most likely thing to make a tester think the app is broken when it is not.

No thumbnails on any speech

Zero poster images exist, and the poster job has a history of failing here. Every card shows a placeholder. Posters are explicitly best-effort and never fail a transcode, so the video itself is fine.

11Troubleshooting

The traps in this stack that cost real hours, each with the symptom that identifies it.

“Something went wrong. Please try again.” on login

Cause: you are on the wrong origin — almost certainly http://localhost:5173 or http://localhost:8080. The backend only accepts https://app.speechcoach.test, so the browser blocks the request and the SPA has no error payload to display, which is why the message is generic rather than specific.

Fix: use https://app.speechcoach.test. Your credentials were never the problem.

A backend change you just made has no effect

Cause: the app container has no bind mount — api/ is copied into the image at build time. The container happily runs the old code and commands succeed against it, which makes this silent and very confusing.

The tell: migrate says “Nothing to migrate” while migration files plainly exist on disk. Or a route 404s that you can see in routes/api.php.

docker compose build app queue-worker scheduler
docker compose up -d app queue-worker scheduler

Exception: api/.env is not baked in — it is injected at container-create time. Env changes need docker compose up -d --force-recreate app, not a rebuild.

https://app.speechcoach.test returns 502

Cause: the host Vite dev server is not running. nginx proxies that hostname to port 5173 on your Mac, and Vite is deliberately never containerized. Fix: cd web && npm run dev.

Nothing starts, and clamav sits at “health: starting”

Cause: ClamAV is loading virus signatures; its startup grace period is three minutes. Both app and queue-worker hard-depend on it being healthy, so the whole stack waits. Fix: wait it out. This is normal, not a hang.

Pages load slowly or a navigation seems to hang

Cause: you are driving the Vite dev server, which compiles modules on demand, single-threaded. Under host load this can stall for a minute or more. It tracks your Mac’s CPU, not the app. Fix: be patient on first load of a route; it is fast afterwards. Known causes already ruled out: dev-server age, stray browser processes, and container load.

Port conflicts on 443, 5433 or 8333

Cause: the end-to-end test stack is running at the same time as the dev stack. They contend for the same ports and must never both be up. Fix: scripts/e2e-stack.sh down first. A leftover Docker network from a previous run can also block startup with a label conflict — check it has no containers attached before removing it.
