# Step 14 retrospective — Production hardening of the deploy

**Executed:** 2026-10-05–06 · **Against:** [STEP-14-deploy-hardening.md](STEP-14-deploy-hardening.md), [MODERNIZATION_PLAN.md](MODERNIZATION_PLAN.md) §12 S14 / §14 observability / §21 containers
**Method:** five parallel build subagents (backend observability, rate-limiting + Larastan, staging/systemd/backup-drill, GlitchTip+Uptime Kuma containers + object-storage hardening, frontend error boundaries), followed by an extensive hands-on reconciliation pass — not a self-report review, a real one: rebuilding Docker images, recreating live containers, and driving the actual demo script end to end — then a sixth dedicated subagent for the Larastan level-8 push once its true size (152 errors, not the ~30 initially visible through a truncating wrapper) was known. Followed, in a second session, by an 8-angle parallel `/code-review high --fix` pass over the full diff (line-by-line scan, removed-behavior audit, cross-file tracer, reuse, simplification, efficiency, altitude, conventions), which caught two real regressions the level-8 push itself had introduced — see "Difficulties encountered" and "Mistakes made" below. Verified for this retrospective by independently re-running every test suite and re-driving the GlitchTip/Horizon proofs myself, not by trusting any agent wave's self-report.

---

## What was accomplished

**Backend (`api/`):**
- `sentry/sentry-laravel` + `laravel/horizon` installed for real (`composer require`, not hand-edited lockfiles). `AssignCorrelationId` middleware (ULID per request, threaded into both the Sentry scope and a new JSON log channel), a double-guarded `/api/debug/throw` demo route, `HorizonServiceProvider` with a `viewHorizon` gate matching `EnsureUserIsAdmin`'s `hasAnyRole(['admin','super_admin'])` convention.
- Four named upload rate limiters (video/avatar/voice-note/coach-document, 10–60/hour), each tested with a real HTTP 429 assertion.
- Larastan raised **5 → 8**, the plan's stated target, with 0 suppressions — every error fixed at its real cause: a `Controller::currentUser()` helper using `abort_if()` (a genuine PHPStan-visible type-narrowing guard, confirmed via Larastan's own extension registration, not a docblock override) for the `$request->user()` nullability pattern across 20+ controllers; `@property-read` overrides on five models for relations the schema's `NOT NULL` FKs already guarantee non-null, verified against the actual migration SQL in each case; two standalone real bugs (a `temporary_path` used past a `whereNotNull` the type system couldn't see through, a `Collection::last()` after an already-guaranteed-non-empty check).
- `media:configure-cors` — discovered already existing and already correct (real S3 API calls, not hand-rolled SeaweedFS JSON) — confirmed live via a real `OPTIONS` preflight. A genuine, previously-unaddressed R10 gap closed: original (`kind='source'`) video rows were never pruned after a rendition was ready; added caption-aware pruning to the existing scheduled `media:reconcile` command.

**Observability containers (`compose.yaml`):** `glitchtip`/`glitchtip-worker`/`glitchtip-migrate`/`glitchtip-db-init`/`uptime-kuma`, all behind `profiles: ["observability"]`, confirmed excluded from a bare `docker compose up -d` by direct `--services` listing. Horizon given **three separate `environments` keys** (`local-default`/`local-transcode`/`local-captions`, mirrored as `production-*`), one per queue-worker container — deliberately not one merged environment, because that would make a container with no `ffmpeg`/`whisper-cli` binary attempt the queue that needs it, breaking the GPL-isolation boundary those separate images exist for.

**Frontend (`web/`):** `@sentry/react` wired to `VITE_GLITCHTIP_DSN` (no-ops when unset — confirmed by code read, exercised by every existing test run since the var is unset by default), a top-level full-page error boundary plus a route-level one around the authenticated layout's `<Outlet>` so a crash in `SpeechWatch.tsx`'s annotation overlay doesn't take navigation down with it. Three new Vitest cases prove the catch.

**Deploy infrastructure (`speechcoach-deploy-target`, the faux-VPS repo):** a second independent shelf, `/srv/speechcoach-staging`, with its own DB (`speechcoach_staging`) and `.env`, reached via `scripts/deploy.sh`'s pre-existing `DEPLOY_PATH` override (no duplicated shelf-swap logic) and a new `.github/workflows/deploy-staging.yml` with its own `concurrency.group` so it can't race production. Five real systemd unit files — `laravel-worker-{default,transcode,captions}@.service` (templated on `%i` = the shelf name, `--environment=production-*` now that Horizon replaces bare `queue:work`, `CPUQuota=150%`/`Nice=19` on transcode per §9.2) plus `laravel-scheduler@.{service,timer}` — honestly documented as unverifiable live inside this Alpine faux-server (no systemd as PID 1), with the install sequence for a real host written into `bin/provision.sh`.

**A real backup/restore drill**, not a described one: `scripts/backup.sh` (`pg_dump -Fc` + a `seaweedfs-data` volume tarball) and `scripts/restore-drill.sh` (scratch Postgres + scratch volume, never touching real data, torn down unconditionally). Actually run: 5s backup, **8s measured restore** against a stated 15-minute RTO, written up in [BACKUP-RESTORE-DRILL.md](BACKUP-RESTORE-DRILL.md) with an honest note that the headroom is today's-toy-data-volume-shaped and should be re-measured once backups move off-box.

**A second-pass code review (`/code-review high --fix`)**, run after the above was believed finished: 8 agents independently scanning the full diff from different angles found two genuine, confirmed regressions the Larastan level-8 push had introduced — see Difficulties #9 below — plus one real static-analysis coverage gap (`config/horizon.php` excluded from PHPStan rather than fixed) and a cron-sweep N+1. All four fixed and re-verified; see Mistakes #3.

## Difficulties encountered

1. **Five parallel agents, five genuinely non-overlapping scopes — and still three real integration bugs at the seams, none visible from any single agent's own all-green report.** Consistent with this project's own standing lesson from STEP-05 (two parallel build agents, a frontend guess at an endpoint the backend hadn't built yet, a backend-only dashboard-query bug, both missed by each agent's own passing self-tests): a reconciliation pass that reads across all five agents' work together, and actually runs it, is not optional ceremony.
2. **`laravel/horizon` needs the real `pcntl` PHP extension, not just a composer platform-req ignore, and nothing in the Dockerfile had it.** `docker compose build app` broke the moment Horizon was `composer require`'d. Fixed in three places independently, because three different build paths each needed to know about it separately: the `vendor` stage's `composer install --ignore-platform-req`, the `runtime` stage's real `docker-php-ext-install`, and `ci.yml`'s `shivammathur/setup-php` extension list (a *fourth*, entirely separate PHP environment from any of the Docker stages) — caught only by actually running `docker compose build`, not by reading the Dockerfile.
3. **`config/horizon.php`'s `defaults` key was shaped wrong and crashed every worker on boot.** Stock Horizon's `defaults` is keyed by supervisor name (`['supervisor-1' => [...]]`); the agent wrote a flat list of bare option names (`['balance' => 'simple', ...]`). `array_replace_recursive()` then merged these as *siblings* of the real supervisor key rather than into it, and Horizon's `toSupervisorOptions()` tried to treat every one of those stray option names as its own phantom supervisor — `Undefined array key "connection"` the moment any worker container started. Caught only by starting the containers and reading their logs; the config read clean in isolation. Fixed by emptying `defaults` entirely, once it was confirmed every option `SupervisorOptions` doesn't receive explicitly already has a safe in-class default.
4. **Pointing `horizon` at a merged `production`/`local` environment key containing all three queues' supervisors would have broken the GPL-isolation boundary `ffmpeg-worker`/`whisper-worker` exist for** — Horizon runs every supervisor in its target environment as children of whichever container issued the command, so the plain `app`-based `queue-worker` container would have tried (and failed) to run transcode jobs needing a binary it doesn't have. Split into three single-supervisor environment keys instead, one per container.
5. **`sentry/sentry-laravel` being installed and correctly configured was not sufficient for anything to reach GlitchTip.** Laravel 11+'s `bootstrap/app.php`-based exception handling requires an explicit `Sentry\Laravel\Integration::handles($exceptions)` call in `->withExceptions()` — without it, exceptions still render and still log (with their correlation id) but silently never report, regardless of a correctly-set DSN. The debug-throw route, the correlation middleware, and the DSN config were all already correct and live; only this one line was missing. Found only by actually driving the full demo script against a real running GlitchTip instance and getting zero events back, not by reading `composer.json`/`config/sentry.php` in isolation.
6. **The systemd-units subagent covered two of `compose.yaml`'s three worker services and missed the third.** `whisper-worker`/captions had no systemd equivalent at all in the first draft — on a real systemd deploy, captions would have silently never generated, with nothing in any log to say why. Caught by re-counting compose's worker services against the directory's file count, not by any test (there is no test that could catch a missing *unit file*).
7. **`docker compose --profile observability down` tears down the entire project, not just the profiled services** — confirmed live, twice, by two different sessions (the container-build subagent self-corrected it once; I reproduced it independently doing the GlitchTip end-to-end proof). `--profile` only scopes which services `up` will *start*; `down` resolves and removes the whole project regardless. The compose file's own comment recommending `down` to stop just these services was actively wrong and has been corrected to `stop`/`rm` instead, which really are scoped.
8. **`docker compose up -d --force-recreate <service>` recreates that container with a new IP, and nginx (the `web` service) does not re-resolve it** — every container recreation in this session that touched `app` needed a `docker compose restart web` immediately after, or every request 502'd. Not a bug introduced this step, just a sharp edge hit repeatedly while verifying it.
9. **The Larastan level-8 push's own `@property-read` overrides introduced two real crash bugs, found only by a second, independent review pass.** `GenerateCaptions.php` and `GenerateDataExport.php` each had an explicit `$speech === null` guard *removed* in favor of trusting a new `@property-read Speech $speech` annotation on `Review`/`SpeechAsset` — but `Speech` uses `SoftDeletes`, and the admin takedown path (`SpeechResource::$record->delete()`) really does soft-delete one, which the `NOT NULL` foreign key the annotation was based on says nothing about. A captions job or data export racing a takedown would have fataled instead of degrading gracefully. Three of the 8 review agents (line-by-line scan, removed-behavior auditor, cross-file tracer) independently converged on the same two files, which is what gave the finding its confidence — a single angle alone might have been a false alarm. Correcting the annotation to `Speech|null` then surfaced the *same* latent assumption, already present before this step, in six more files (`ReviewResource`, three review notifications, `AnnotationPolicy`, `FfmpegTranscoder`, `FakeTranscoder`, `VoiceNoteService`) — all fixed with a null-check appropriate to each context (silent no-op for posters, `fail()`/terminal status for transcode and captions jobs, a generic fallback string for notifications, and routing `AnnotationPolicy` through the already-denormalized `speech_owner_id` column instead of the relation at all).

## Mistakes made

1. **I initially trusted a JSON-wrapped PHPStan summary that silently truncated at "the first several files" with a buried `"truncated":true` flag**, and almost scoped the Larastan level-8 push as "~30 errors" before re-running with `-v` and finding the real number was 152 across 33 files. Worth remembering generally: a tool's own summary of its output is not the output, especially when nothing about its shape visibly signals truncation until you grep for the flag.
2. **Every live verification in this retrospective required actually running something** — none of the real bugs above (the Horizon config shape, the missing `Integration::handles()` call, the missing captions unit, the `--profile ... down` footgun, the `pcntl` build break) were visible from reading the code in isolation, all five build subagents' own code reads included. This step is as strong a confirmation as any in this project of the standing rule: a script, a config, or a container that has never actually been started is a hypothesis, not a fact.
3. **The retrospective above was originally written and believed accurate before the Larastan level-8 push's own two crash-bug regressions (Difficulties #9) were found.** Passing `pint`/`phpstan`/`pest` cleanly is not the same claim as "no bugs were introduced reaching that state" — a type-level annotation can make the checker happy while being factually wrong about runtime nullability, and nothing about a green CI run would have caught it. The actual catch came from a second pass with a genuinely different method (8 independent review angles over the diff, several converging on the same files) rather than from re-running the same verification loop again. Also caught in the same pass: `config/horizon.php` had been quietly excluded from PHPStan's `excludePaths` to hide one real, fixable `env()` type gap rather than fixing it — "level 8, clean" was true only because one file had been carved out of the check, which the plan's own stated target (level 8 across the codebase) did not intend.

## Package/tooling surprises

- GlitchTip's Django app namespaces are `apps.organizations_ext`/`apps.projects`/`apps.issue_events`, not the shorter names a casual guess would reach for (`organizations_ext`, `issues`) — only discoverable by introspecting `django.apps.apps.get_app_configs()` inside the running container, not from any doc skimmed externally.
- GlitchTip's own `IssueEvent` model uses `timestamp`, not `received`, as its ordering field — again only found by introspecting the model's real field list after a first guess threw `FieldError`.
- Horizon's `--environment=` CLI option is real, documented in its own command signature (`{--environment= : The environment name}`), and genuinely overrides the normal `config('app.env')`-based resolution — this is what makes three containers sharing one `config/horizon.php` but each supervising only its own queue possible at all.
- Larastan registers `abort_if()`/`abort()` as real flow-sensitive type-narrowing extensions, not something that needs a `@var` override to convince — confirmed by the level-8 subagent with an isolated test file before committing to that idiom across 20+ files, rather than assuming.

## What was not verified — and cannot be, from here

- **Uptime Kuma's actual pairing with a free external check.** Beyond needing a human to sign up for a third-party account, there is currently no publicly-reachable URL for any external service to poll — `app.speechcoach.test`/`api.speechcoach.test` only resolve via this machine's own `/etc/hosts`. This is the one acceptance item that is structurally blocked by "no real host has been purchased yet" (STEP-14's own "Deliberately stubbed: no CDN, no autoscaling, no blue-green. One box" framing, and STEP-02's original scope split, both describe exactly this situation) rather than by anything left undone. **To close it once a real host/domain exists:** sign up for a free tier (UptimeRobot's 50-monitor free plan or Better Uptime's free tier are the usual choices), point it at the real `/up` health endpoint over HTTPS, and add its status badge/webhook into the Uptime Kuma instance so both the internal and external views are visible from one place.
- **The GitHub Actions `deploy-staging.yml` workflow itself was never triggered by a real push** — the faux-server deploy mechanism it invokes was proven directly by hand instead, which is strong evidence but not the same as watching the real Actions run go green. The existing `deploy-production` job has the same caveat from CP-02 and was not re-verified this step either.
- **The `staging` GitHub Environment does not yet exist in the repo's Settings** — per this project's own established pattern for `production` (`CP-02-deployment-and-secrets.md`: "Settings → Environments → New environment"), someone needs to create `staging` and populate its `DEPLOY_HOST`/`DEPLOY_KEY`/`DEPLOY_HOST_KEY` before `deploy-staging.yml` can run for real; right now it would fail on missing secrets, not deploy anything wrong.
- **The systemd units were never live-verified by `systemctl`**, by this Alpine faux-server's own architectural limit (no systemd as PID 1) — correctness was checked against `systemd.service(5)`/`systemd.timer(5)` semantics and against the exact Compose commands they mirror, not by a real `systemctl status`.
- **Horizon's dashboard was proven to report accurate live data** (masters, workload, a real failed job with stack trace) **but was not screenshotted/driven through a real browser session** — the proof was via its own JSON API, which is what the dashboard itself also calls, but a human has not looked at the rendered page.
- **No controller-specific unauthenticated-401 test exists for most of the 20+ controllers `Controller::currentUser()` now guards** — the `auth:sanctum` middleware guarantee itself is tested elsewhere (`/me`), but the Larastan subagent was honest that this makes the new guard real defense-in-depth rather than something the test suite formally proves unreachable. Named here rather than overclaimed.
- §11.1's legal groundwork remains entirely unaddressed — unrelated to this step, carried forward since STEP-11.
