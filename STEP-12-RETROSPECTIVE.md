## Difficulties encountered

1. **Filament could not be installed by the sandboxed build agent at all** — no outbound network access to Packagist in that environment. Rather than declare an unresolvable dependency (which would have broken `composer install --no-dev` in the Docker `vendor` stage for every other image), the agent correctly wrote the full Filament source tree unregistered, with an exact docblock of finish-up steps. A later pass in this same session, with real network access, found `packagist.org`'s legacy v1 metadata endpoint (`packagist.org/providers/ext-intl.json`) is unreachable from this box while `repo.packagist.org`'s real v2 API works — `--ignore-platform-req=ext-intl` was the correct workaround, not a proxy/mirror change.
2. **Three real bugs only surfaced once Filament actually booted**, none catchable by reading: `AppAuthentication` has no `required()` method (`Panel::multiFactorAuthentication()`'s own `isRequired` parameter is the real API); all four Filament Resources had no `getPages()` override, and the base `HasPages` trait's default is an empty array — zero routes registered for any of them until `ManageRecords`-based Page classes were added; `Review` has no `annotations()` relation in this codebase (every existing caller queries `Annotation::where('review_id', ...)` directly), so `SpeechResource`'s grouped-annotations view had to be rewritten to match that convention rather than adding a new relation to a heavily-used core model.
3. **The `clamav` healthcheck command doesn't exist on Alpine.** The build agent wrote `clamdcheck.sh` (standard ClamAV documentation), but that script ships only with Debian/Ubuntu's `clamav-daemon` package — confirmed by building the image and searching it. `clamdscan --ping 1` is the real equivalent available on Alpine, confirmed working end-to-end (genuine Docker `healthy` status).
4. **The `/code-review` pass (8 parallel finder agents, explicitly asked to check RBAC) found two critical, live security holes** that the build-and-reconciliation-audit process above had missed entirely, because that audit checks the *seam* between two build agents' code, not bugs internal to one agent's own logic: `RoleAssignmentService::assign()` used `syncRoles([$role])`, which **replaces** a user's entire role set — approving a coach application for an admin would have silently stripped their admin role with zero last-admin check, the exact bug class this whole step exists to prevent. And **none of the Filament `UserResource` actions ever called `Gate::authorize()`** — `UserPolicy::suspend()`'s self-exclusion was dead code, and the real UI let an admin suspend themselves (`UserDeletionService::suspend()` also lacked the self-exclusion check `softDelete()` already had).
5. **The e2e CI failure for `verify-postgres-last-admin-lock.sh` required actually standing up the full local stack** (`./scripts/e2e-stack.sh up --fresh`) to diagnose, because the GitHub Actions log view truncated the real error. Three compounding bugs, found only by running it: `User::factory()` needs Faker, which isn't installed in the production (`--no-dev`) `app` image (Laravel's own `fake()` helper is guarded by `class_exists(\Faker\Factory::class)` and is never even defined there); plain `create()`/`updateOrCreate()` with `username`/`email_verified_at` throws `MassAssignmentException` since those columns aren't in `User`'s fillable list (and `E2ESeeder::seedUsers()` has this exact same latent bug, unfixed, flagged for later); and the real methodology gap — the script assumed its two seeded users were "the last two admins," but `E2ESeeder` had already seeded a real admin+super_admin pair earlier in the same stack, so both concurrent revokes trivially succeeded (a false pass, not a broken lock) until the script was fixed to demote every other admin first.

## Mistakes made

1. **A same-session self-inflicted regression, caught by the next review pass.** The reconciliation-audit fix pass added `credential` to `PublicProfileResource` using `getRoleNames()->first()` — copying `ReviewerDirectoryResource`'s convention verbatim — without noticing that `/api/u/{username}` is **fully unauthenticated**, unlike the reviewer directory (which sits behind `RequireAuth`). This leaked `admin`/`super_admin` role status to any anonymous caller, enabling enumeration of real site administrators. The `/code-review` pass caught it a few hours later in the same day. **Standing rule this generalizes to: reusing a field-computation convention from one resource on another resource requires checking that resource's own auth boundary, not just copying the expression** — the same `getRoleNames()->first()` call is correct behind auth and a leak in front of it.
2. **`RoleAssignmentService::assign()`'s docblock asserted a safety property ("an ADDITION can never reduce the admin count") that its own implementation violated** (`syncRoles` vs. `assignRole`). The comment was written first, describing the intent, and the code didn't match it — worth remembering that a docblock claim next to the code it describes is not evidence the code satisfies it; this is exactly the kind of claim `/code-review`'s RBAC-focused pass exists to catch, and did.
3. **The `verify-postgres-last-admin-lock.sh` script was written and judged "logically sound" during the original reconciliation audit, based on reading it, not running it.** Every one of its three real bugs (Faker, mass assignment, the false-pass methodology gap) was invisible on read and only surfaced by actual execution against a real Postgres. Consistent with this project's now well-established pattern: **a script or test that has never been run is a hypothesis, not a fact**, regardless of how carefully it was reasoned about.

## Package/tooling surprises

- `filament/support` genuinely requires the PHP `intl` extension, which the official `composer:2` Docker image (used for the `vendor`/`vendor-dev` build stages) does not bundle — `--ignore-platform-req=ext-intl` on those two stages' `composer install` calls is correct and safe specifically because the `runtime` stage those images are built from already installs `intl` for real; this is a build-stage-vs-execution-stage distinction, not a missing dependency.
- Laravel's `fake()` helper is conditionally defined (`class_exists(\Faker\Factory::class)`), which this project had apparently never hit before STEP-12 despite it being a structural fact about every production (`--no-dev`) image since Step 00 — `E2ESeeder` has silently depended on its own fixture rows already existing from an earlier valid seed rather than genuinely being re-seedable from an empty table, which is now flagged (not fixed) for a future pass.
- Filament 4.12.6's real API differs from the plan-writing session's best guess in one place: `isRequired` is `Panel::multiFactorAuthentication()`'s own third parameter, not a chained method on the provider — unverifiable without a real install, and this session did get a real install.

## What was not verified — and cannot be, from here

- **No real-browser/Playwright verification of the Filament panel UI** — the 2FA TOTP setup flow, the coach-application queue's document-viewer modal actually opening a new tab, table filters/sorting — same category every prior step's rich-interaction work has left open (jsdom/jest can't drive a real Livewire/Alpine.js panel any more than it can a real ProseMirror editor).
- **No HTTP-level test asserts 403 from `/control-panel` for a non-admin.** The middleware logic was read directly and is correct, and is now the second time this session that logic-looks-right was insufficient elsewhere (see Mistakes) — this specific gap is named here rather than assumed closed.
- **"Suspend a user, their session dies within one request" has no test at all** (grep confirms). The `suspended_at` column is stamped correctly and every auth check that should read it does, per code inspection, but no test proves the actual session-death behavior end-to-end.
- **The whisper.cpp/ffmpeg-worker container images were not touched this step** and remain as previously verified (or not) in STEP-04/09's own retrospectives — out of scope here.
- **This session's fixes were pushed to `origin/development`** (confirmed: `origin/development` HEAD matches local HEAD at `8e56849`), but the actual GitHub Actions run for that final push was not independently re-checked from here (no `gh` CLI access in this environment) — the local four-run reproduction against a real Postgres is strong evidence, not a substitute for watching the real CI job go green.
- §11.1's legal groundwork remains entirely unaddressed — unrelated to this step, carried forward from STEP-11.
