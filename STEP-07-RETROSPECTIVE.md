# Step 07 retrospective — Write the commentary

**Executed:** 2026-08-15 · **Against:** [STEP-07-write-commentary.md](STEP-07-write-commentary.md), [MODERNIZATION_PLAN.md](MODERNIZATION_PLAN.md) §8.4 / §10.2 / §10.4 / §11.2 / §12 S7
**Method:** heavier than Steps 05/06's plain parallel-build-then-audit, because a four-agent readiness review found the step's own text left real contract ambiguities unresolved (not just risky-to-guess) before any code was written. In order: (1) four parallel read-only readiness-review agents — backend, frontend, database/schema, cross-cutting seams — against the unbuilt step; (2) two direct code checks resolving the biggest open questions (`Annotation::scopeVisibleTo` already lets a reviewer see their own drafts; `AppServiceProvider`'s admin-bypass list already pre-reserved `annotation.create`/`annotation.update`/`review.publish` as ability names); (3) those findings written up as a frozen contract (exact endpoints, `conflictSource: "self"` semantics, publish-count-as-delta, `OverlayStack`'s new `draftIds` prop, Undo-as-re-POST-not-a-restore-endpoint); (4) two parallel build agents (backend, frontend) against that contract; (5) an independent reconciliation-audit agent, which reported **zero confirmed bugs**; (6) a separate `/code-review high` pass (8 parallel finder agents across different angles — conventions, simplification, dedup, altitude, efficiency, and two rounds of correctness) run afterward at the user's request, which **did** find 9 real, fixable bugs the reconciliation audit had missed; (7) a manual verify-then-fix pass on those findings, re-validated fresh.

## What was accomplished

**`api/`:**
- `app/Http/Controllers/Api/AnnotationController.php` — `store`/`update`/`destroy`/`clearMine` added alongside the existing STEP-06 `index`. Every write route derives the caller's own review from `(speech, $request->user())` via `ReviewService::findOwnReview` — never a client-supplied `review_id` — matching STEP-07's explicit "no `authorId` parameter" requirement generalized to all four write routes, not just `clearMine`. `{speech}` is resolved through a private `resolveSpeech()` (`Speech::withTrashed()->findOrFail()` + a trashed check) rather than implicit route-model binding, specifically so a soft-deleted-but-found speech returns 410 instead of the default 404.
- `app/Exceptions/{AnnotationConflictException,AnnotationCapExceededException,SpeechDeletedException}.php` — each with its own `render()`, mirroring the existing `SelfReviewNotPermittedException` pattern. `AnnotationConflictException` renders 409 with `{ message, conflictSource: 'self', current: AnnotationResource }` — `conflictSource` is hardcoded to the literal string `'self'` with a code comment explaining why: annotations are single-writer-per-review (only that review's own reviewer can ever pass the write policy), so any `lock_version` mismatch is definitionally the same reviewer's other tab/session, never a different person.
- `app/Services/AnnotationService.php` — `create`/`update`/`delete`, each `DB::transaction` + `lockForUpdate()`, mirroring `ReviewService`'s established pattern exactly. `create` is idempotent on `(review_id, client_uuid)` scoped to live rows (the partial unique index STEP-06 already shipped), enforces the ≤200-per-set cap against the `annotations_count` counter cache under the same lock (never a live `COUNT(*)`), and calls `ReviewService::recordAnnotationActivity` in the same transaction as the insert. `delete` calls `$annotation->delete()` on a model instance (never a bulk query-builder delete) so `Annotation::booted()`'s `deleting` listener actually fires.
- `app/Models/Annotation.php` — `booted()` registers a `deleting` listener that decrements `reviews.annotations_count` (and `published_annotations_count` if the deleted row was published) inside the same transaction, confirmed via Laravel's own vendor source (`SoftDeletingScope`) to be skipped by bulk deletes — which is exactly why `clearAnnotations` (below) resets both counters explicitly rather than relying on this listener.
- `app/Services/ReviewService.php` — three new methods: `findOwnReview` (moved out of the controller during the code-review fix pass, so the controller stays a thin caller the way `AnnotationService` already is), `recordAnnotationActivity` (`accepted → in_progress` on the first annotation, counter increment, no lock of its own — deliberately reuses the caller's already-held lock), `publish` (bulk `UPDATE ... WHERE published_at IS NULL`, delta read directly off the affected-row count, `first_published_at`/`last_published_at`/`status`/`last_transition_at` all updated in one transaction), `clearAnnotations` (bulk soft-delete + explicit counter reset to 0, `status`/`revoked_at`/`reviewer_id`/`responded_at` deliberately untouched).
- `app/Policies/{AnnotationPolicy,ReviewPolicy}.php` + new `app/Policies/Concerns/GrantsReviewWriteAccess.php` — `create`/`update`/`delete` (Annotation) and `publish`/`clearAnnotations` (Review) all delegate to one shared `reviewerOwnsActiveReview()` trait method (categorical admin denial, `revoked_at` check, `Review::ACCESS_GRANTING` check) instead of five independent copies — this was a code-review fix, not part of the original build.
- `app/Providers/AppServiceProvider.php` — `Gate::define` for all five new abilities, with `annotation.delete` and `review.clearAnnotations` added to `$mustFallThrough` (the two that weren't already pre-reserved from STEP-05/06). Verified — not just written — by a dedicated test that forces a review row onto an admin id and asserts 403 across all five abilities, both at the policy-unit and HTTP level.
- `app/Http/Resources/AnnotationResource.php` — additively extended with `lock_version`/`client_uuid`; the STEP-06 "frozen contract" docblock now says so explicitly rather than silently going stale.
- `database/migrations/2026_08_09_100001_create_reviews_table.php` — `ck_reviews_counters_nonnegative` added to the SQLite branch (it previously existed only on PostgreSQL — a real driver-parity gap a database-readiness-review agent found: a counter-decrement bug could have passed CI on SQLite and only surfaced in production).
- `tests/Feature/Annotation/AnnotationWriteHttpTest.php` (20 tests) + `tests/Feature/Review/AnnotationCounterCacheTest.php` (7 tests) — new. Plus fixes to `UserFactory`/`ReviewFactory` surfaced by turning on `preventSilentlyDiscardingAttributes`/`preventAccessingMissingAttributes` (§10.4's "alongside it," not previously enabled).

**`web/`:**

## Difficulties encountered

**A clean reconciliation audit is not the same as a clean codebase.** The dedicated reconciliation-audit agent (step 5 of the method above) reported zero confirmed bugs, re-running every test suite fresh and independently verifying the highest-risk items (the admin-bypass list, the response-envelope asymmetry, the `SoftDeletingScope` bulk-delete-skips-events claim). That audit is oriented around one specific failure mode — *does the frontend's guess about the backend's shape match reality* — and it did that job well. A separately-angled `/code-review high` pass, run afterward at the user's request with finder agents oriented around correctness/simplification/efficiency/duplication rather than contract-matching, found 9 additional real bugs the reconciliation audit's own angle couldn't have caught (a stale `lockVersion` when a row is edited via a second write path, a remount race that could drop in-flight keystrokes, missing `pointercancel` handling, an optimistic-revert-on-delete-failure bug, an Undo handler with no error handling, and others — see "Mistakes made"). **The standing rule this establishes: a reconciliation audit checks the seam between two agents' work; it does not substitute for a general code-quality/correctness review of either side individually.** Both are worth running, and neither is redundant with the other.

**One finder-agent claim needed empirical verification, not just a read, before it could be trusted or reported.** A finder claimed `AnnotationPolicy::update`/`delete` would throw a `LazyLoadingViolationException` on every write request outside production, reasoning from `Model::preventLazyLoading()` being enabled in this codebase's `AppServiceProvider`. Reading the code alone made this plausible. A throwaway probe test (`Annotation::query()->findOrFail($id)->review` on a freshly-fetched, no-relations-loaded instance, run inside the actual test harness) proved it does not throw — contradicting a claim that was internally consistent with the code but wrong about Laravel's actual runtime behavior. The claim was refuted before being reported, not reported-then-corrected. **Standing rule: a finder agent's prediction about framework/library runtime behavior is a hypothesis, not a fact, until it's actually been run.**

**A GitHub branch-protection required-checks mismatch surfaced when opening this step's PR**, unrelated to STEP-07's own code but real, encountered-in-the-wild process friction: `ci.yml`'s `push:` trigger has no branch filter (unlike CP-12's own documented example, which restricts it to `main`), so pushing to a PR branch fires both `push` and `pull_request` for the same commit. GitHub disambiguates by appending `(pull_request)`/`(push)` to the check name, but the branch protection rule's required-checks list still names the old, unsuffixed `ci / e2e`/`ci / test` strings — so those two required checks can never be satisfied by any run, ever, and show as "pending" indefinitely rather than failing loudly. Diagnosed and multiple fix paths (UI re-selection, direct REST API call) were provided; **not yet confirmed resolved** as of this retrospective, since it requires the user's own GitHub credentials to execute (deliberately not worked around by pulling a credential out of the local git credential helper without explicit authorization for that specific use). This is exactly the failure mode CP-12-required-checks.md's own "You will hit this" section warns about, encountered for real rather than as a hypothetical.

## Mistakes made

Nine real bugs shipped past the two build agents' own self-reports *and* the dedicated reconciliation audit, caught only by the differently-angled `/code-review high` pass:

1. **`useAnnotationEditor`'s `lockVersion` never resynced against a second write path for the same row.** `TimelineStrip`'s drag-to-retime PATCHes directly, bypassing the hook; an already-open row editor kept the `lock_version` it mounted with, so its next autosave 409'd against its own just-applied external change. Fixed by extracting the existing `BroadcastChannel`-driven "external update" handling into a shared `applyExternalUpdate` function, now also called from a new effect keyed on `initial.lock_version`.
2. **A remount race could silently drop in-flight keystrokes.** `Composer` remounts its `useAnnotationEditor` instance with a fresh key the moment a create succeeds; if the coach kept typing during the in-flight POST, the remount's cleanup cancelled the pending debounced save *and* the success path cleared the localStorage backup, discarding text with no recoverable copy. Fixed by comparing the just-saved snapshot against the live fields at resolution time and, on a mismatch, re-scheduling a flush instead of finalizing to `'saved'`.
3. **The Undo toast's re-create call had no error handling** and permanently latched after one click attempt, so a failed un-delete left the note gone with no way to retry. Fixed with a three-state (`idle`/`pending`/`done`) guard instead of a one-way boolean.
4. **`TimelineStrip`'s drag handlers never listened for `pointercancel`**, so an interrupted touch-drag left `window`-level listeners attached indefinitely, misfiring on later unrelated pointer movement. Fixed by adding a `pointercancel` handler that cleans up and restores the pre-drag position.
5. **`AnnotationList`'s delete handler stripped the live-preview override before the DELETE request resolved**, so a failed delete left an open editor's live preview silently reverted to stale content. Fixed by only removing the override after confirmed success.
6. **`AnnotationController::resolveOwnReview` queried `Review` directly** instead of going through `ReviewService`, breaking this same step's own established rule (`AnnotationService`'s docblock: the controller must never touch the model directly). Moved into `ReviewService::findOwnReview`.
7. **Five near-identical copies of the same authorization check** across `AnnotationPolicy` and `ReviewPolicy`, independently flagged by three separate review angles. Extracted into `GrantsReviewWriteAccess`.
8. **A missing sort tiebreak** in `AnnotationComposerPanel`'s "current annotation" lookup — the only one of three call sites without the `id` tiebreak the other two had, meaning two same-`start_seconds` annotations could disagree on ordering between "what's highlighted" and "what's displayed." Deduped into a shared `compareByStartThenId`.
9. **A redundant same-row query, up to three times, on a single PATCH/DELETE request** (controller, then the policy's lazy `$annotation->review` load, then the model event's own locked re-fetch). Cut to two via `setRelation`.

Three additional findings were deliberately **not** fixed, on the grounds that the user's ask was "logic and syntax errors," not a broader refactor — recorded via `ReportFindings`' `outcome` field rather than silently dropped: counter-cache maintenance remaining scattered across four independent methods (backed by a working, now driver-parity-fixed DB `CHECK`, so a real refactor risk for a style-only win); the composer tree's lack of memoization and `TimelineStrip`'s un-batched `pointermove`→state updates (a real perf concern, out of scope for a correctness pass); and a second hand-rolled debounce duplicating `useUsernameAvailability.ts`'s existing pattern.

## Package/tooling surprises

`@base-ui/react`'s `toast` and `alert-dialog` modules were already present in `node_modules` (the package itself is a STEP-05/06-era dependency, used there for `button`/`progress`/`badge`) but had never been wrapped or used — this step is the first to need a toast/dialog primitive at all, and the readiness-review pass found the unused modules before any component was built against them, avoiding a second library being pulled in for the same job.
