Start here

The one-minute version

A speaker uploads a private video, invites specific people, and receives feedback tied to exact moments. The system keeps the video safe, prepares it in the background, and shows the right note at the right second.

Imagine a private school theater. The speaker owns the stage. Invitations are tickets. A reviewer gets one folder for that performance and puts sticky notes at exact times: “Great pause at 1:23.”

A React single-page app calls a Laravel JSON API. PostgreSQL stores relationships and permissions; SeaweedFS stores media; Valkey queues work; FFmpeg and Whisper workers process video and captions.

The surprising shortcut: large video bytes do not travel through Laravel. Laravel gives the browser a temporary, narrowly scoped permission slip. The browser then uploads to or watches from SeaweedFS directly.

This is a modular monolith—not microservices

There is one Laravel application and one business model. The separate containers are different jobs or infrastructure, not independent mini-products with separate databases and APIs. That keeps reasoning simple while isolating heavy work.

One school has many rooms: office, library, warehouse, workshop. It is still one school.

One deployable domain codebase serves HTTP and queue commands. Process boundaries isolate workload and dependencies.

The production web container serves the built React files with Nginx and forwards API requests to PHP-FPM. During development, Vite runs on the host for fast refresh.
Product shape

The most important design decision

The Review row is both the reviewer’s permission to enter and the folder containing that reviewer’s work.

Speakerowns a speech
→
Speechprivate video + details
→
Reviewinvite + access + work
Reviewerthe invited person
→
Review folderone person × one speech
→
Feedbackannotations + essay

A theater ticket has a person’s name and one show on it. The ticket opens the door. The same ticket number is printed on that person’s feedback folder. No ticket means no folder and no notes.

Why this shape is powerful

  • An annotation must belong to a review, so an unauthorised “orphan note” cannot exist.
  • One database rule allows only one review per person per speech.
  • Revoking the review removes the access grant at the same boundary that owns the feedback.
  • Reviewers cannot see one another’s folders or even use the reviewer count as a clue.
Make wrong states impossible to represent, not merely forbidden in a document.

How the check happens

1

Who are you?

The session cookie identifies the signed-in account.

2

What do you want?

The API route and request say “watch speech 42” or “edit note 7.”

3

Are you allowed?

Laravel policies inspect ownership, roles, and review state.

4

Only then act

Return data, sign a media URL, or make a change.

A session is a coat-check ticket matched against a live guest list. Cross your name off the list and your next request is refused.

Sanctum/Fortify use stateful SPA sessions. Policies enforce record-level access; role checks handle capabilities.

Why sessions instead of JWTs?

This product often needs to take access away now: revoke a reviewer, suspend an account, or remove a role. A session is checked against server state on every request. A self-contained JWT remains valid until it expires.

Important nuance: a media link already issued is temporary, not magically recallable. Its short lifetime limits the remaining window, and Laravel refuses to issue a new link after access is revoked.

Backend

What Laravel does

Laravel is the rule-keeper and coordinator. It should decide and record—not carry 200 MB videos through the office.

1

Route

Matches the URL and HTTP action to a controller.

2

Middleware

Checks session, CSRF protection, verification, and shared rules.

3

Policy + validation

Checks permission and whether submitted data has the right shape.

4

Service / model

Runs the use case, changes data, signs storage, or dispatches a job.

A concrete example: “Invite Jordan”

  1. The browser sends a request to create a review for a speech.
  2. Authentication proves who is making the request.
  3. The speech policy proves that person owns the speech.
  4. Validation proves Jordan is a valid reviewer and not a duplicate.
  5. The review service creates the invitation in a transaction.
  6. Laravel queues a notification and returns a safe JSON resource.

Seams are intentional

Controllers stay thin: HTTP details in, response out. Reusable business work sits in services.

Policies stay central: a second screen cannot accidentally invent a different access rule.

Storage is abstracted: app code names a disk/path rather than hard-coding SeaweedFS everywhere.

Jobs are explicit: slow operations have statuses, retries, failure codes, and recovery.

Safe responses: API resources decide what leaves the server. Internal paths, command output, and detailed worker failures do not belong in user-facing JSON.
Data

Why PostgreSQL and object storage have different jobs

Ledger

PostgreSQL

Excellent at relationships and questions:

  • Who owns this speech?
  • Did this reviewer accept?
  • Which notes are published?
  • Is this the one primary video?
Warehouse

SeaweedFS

Excellent at large byte objects:

  • Original upload
  • Playable MP4
  • Poster image
  • WebVTT caption file

A library catalogue holds the title, owner, and shelf number. The actual giant book stays on the shelf. Stuffing the book into the index-card drawer would ruin the catalogue.

Why video does not live in PostgreSQL

  • Video seeking needs byte-range reads: “give me this small slice now.” Object storage speaks that language.
  • A large video read should not throw useful database pages out of memory.
  • Database backups stay focused on valuable relational facts instead of huge replaceable media bytes.

What PostgreSQL protects even if app code slips

Foreign keys

A note cannot point to a review that does not exist.

Unique rules

One reviewer cannot get two folders for one speech.

Checks + partial indexes

Only valid states and one primary asset of each kind.

The trade-off: the database write and file write cannot be one transaction. Asset statuses such as uploading, processing, ready, and failed make that gap visible and repairable.
Journey 1

Uploading a video

Laravel authorizes and coordinates. Uppy and the browser carry chunks directly to SeaweedFS.

1

Ask

React asks Laravel to create a speech and start an upload.

2

Get passes

Laravel creates an asset row and signs temporary multipart upload URLs.

3

Carry chunks

The browser sends chunks directly to SeaweedFS. Interrupted chunks can resume.

4

Confirm

Laravel verifies completion and places processing jobs on queues.

The principal writes a hall pass. The moving company carries boxes straight to the warehouse. The principal records that the delivery arrived but never lifts every box.

Why multipart upload?

A 200 MB video is split into pieces. If hotel Wi-Fi fails after piece 17, only unfinished pieces need to be retried. The server also avoids request-size and memory bottlenecks.

Then two lanes begin

Video lane

FFmpeg worker

Inspects the source. It remuxes a compatible file or transcodes an incompatible one into browser-friendly MP4, then makes a poster.

Caption lane

Whisper worker

Extracts speech audio, runs local whisper.cpp, writes captions, and produces searchable transcript data.

User-experience win: the playable video can become ready while captions are still processing. Slow transcription does not hold the video hostage.

Journey 2

Watching a private video

1

Open speech

React asks the API for speech information.

2

Check grant

Laravel confirms owner, active review access, or moderation authority.

3

Sign URL

Laravel returns a short-lived storage URL for the ready video.

4

Stream

The browser requests only the byte ranges needed for play and seek.

The principal checks your ticket and gives you a temporary key to one locker. The key cannot open the whole warehouse and soon stops working.

The API returns a presigned GET URL. SeaweedFS serves HTTP Range requests directly to the browser’s <video> element.

Why Range matters

Dragging from 00:10 to 08:45 should not download the first eight minutes again. The player asks storage for the byte section around 08:45. That makes scrubbing responsive and is a major reason media bytes belong in object storage.

When the temporary URL expires

The player adapter can request a fresh authorized URL and restore playback state. A refresh is another chance for Laravel to deny access if the review was revoked.

Security boundary: a signed URL is a short-lived capability. Treat it like a temporary key: limit its object, method, and lifetime; never log or expose it unnecessarily.

What Laravel does not do

No video proxy

PHP is not continuously relaying the stream.

No public bucket

Storage objects are not simply open to everyone.

No permission cache

Revocation checks should use current authority.

Journey 3

Timed feedback: the heart of the product

Each annotation has a start, duration, text, and review. The player shows it only while its time window is active.

Video time83.2 seconds
+
Annotationsstart and end times
→
Active Setnotes visible now

A teacher has sticky notes saying “show from 1:20 to 1:26.” A tiny clock helper checks the stopwatch and holds up exactly the notes whose time has arrived.

Two timing signals, one answer

Browser TextTrack

The native timed-text machinery reports active cues accurately when the browser behaves.

Pure reconciler

computeActive(cues, currentTime) independently calculates the active IDs several times per second.

The overlay renders from the reconciled active set. CSS handles the fade, which lets the browser’s compositor do smooth visual work without turning animation into application state.

Why the pure function matters

  • It can be tested with numbers—no real video, network, or browser timing required.
  • Seeking backward, overlap, exact boundaries, and bad inputs become cheap test cases.
  • The browser integration becomes a small adapter around proven arithmetic.
Authoring loop: a reviewer pauses at a moment, writes, autosaves a draft, previews the same overlay the speaker will see, then publishes the review as a coherent snapshot.
Journey 4

Captions and transcript

Captions are automatic by default, editable by the speaker, and processed locally so speech recordings do not need to go to a transcription vendor.

1

Extract

The worker uses FFmpeg to make transcription-friendly audio.

2

Listen

Pinned whisper.cpp code and pinned model weights turn audio into timed words.

3

Store

WebVTT goes to object storage; transcript data and provenance go to PostgreSQL.

4

Use

The player shows captions; transcript clicks seek; search finds spoken phrases.

A robot listens and makes a first draft. The speaker is the editor because robots mishear names and accents.

The worker writes a VTT asset and a derived transcript projection. Manual VTT edits trigger transcript re-derivation.

Why keep both VTT and transcript data?

RepresentationBest atLives in
WebVTT fileNative player captions with time cues.SeaweedFS
Transcript projectionSearch, transcript panel, click-to-seek, later analysis.PostgreSQL

Why pin the engine and model?

The same audio can produce different words after an invisible model upgrade. The system records model/engine provenance so changes are deliberate and results are explainable.

Owner control: the caption setting is an owner-only switch. Disabling automatic generation must not silently delete an already useful, ready caption file.
Background work

Why queues and workers exist

A web request should answer in seconds. Video conversion and speech recognition can take minutes, so they become jobs.

A restaurant cashier takes your order quickly and puts a ticket on the rail. The soup cook, pizza cook, and dessert cook each pull from the right lane. You do not stand at the cash register while the pizza bakes.

Three lanes with different clocks

LaneWorkerTypical workWhy separate?
defaultqueue-workerNotifications and short projection work.Fast jobs should stay fast.
transcodeffmpeg-workerProbe, remux/transcode, poster.Long timeout; FFmpeg dependency.
captionswhisper-workerAudio extraction and transcription.CPU-heavy; model and CLI dependency.

Reliable-job vocabulary

Idempotent

Running the same job twice should not create two primary videos or corrupt the result.

Attempt identity

An old caption worker must not overwrite a newer retry or manual edit.

Visible status

The UI can show uploading, processing, ready, or a safe failure code.

Reconciliation

The scheduler detects work stranded by a killed worker and repairs or fails it safely.

Key principle: queues do not guarantee “exactly once.” Correctness comes from database constraints, current-attempt checks, transactions, and safe repetition.

Why so many containers?

A container is a repeatable lunchbox: the program plus the tools it needs. Multiple lunchboxes do not automatically mean microservices.

Image vs container

An image is a lunch recipe. A container is one packed lunch made from it. The app, quick worker, and scheduler can use the same recipe but run different commands.

The multi-stage Dockerfile builds dependency, web, runtime, FFmpeg, and Whisper targets. Compose supplies commands, networks, volumes, dependencies, and health checks.

Persistent volumes: containers are replaceable; database, media, and model files live in named volumes so replacing a process does not erase its durable data.
Correctness

How the design resists mistakes

Authorization at the server

Hiding a button is friendly UI, not security. Laravel policies must reject the request itself.

Transactions

Changes that belong together either commit together or roll back together.

Database invariants

Foreign keys, uniqueness, checks, and partial indexes guard facts under concurrency.

Optimistic locking

Multi-writer documents use a version number so one tab cannot silently erase newer work.

Safe failure codes

Users receive stable explanations; private paths and worker stderr remain internal.

Recovery sweeps

The scheduler finds stale processing attempts after hard crashes.

Example: two tabs edit the same essay

1

Both read v5

Tab A and Tab B start from version 5.

2

A saves

The database writes A’s text and advances to v6.

3

B tries v5

The server sees B is based on an old version.

4

Conflict, not loss

B reloads or resolves; A’s work is not silently overwritten.

Two children copy the same worksheet. One hands in a new answer. The second must not erase it using an older copy without being warned.

The frontend makes the experience pleasant. The backend and database make the rules true.

Test a ruler with measurements, a lock with the wrong keys, and the whole bicycle with a real rider. Do not make the rider test every screw.

The honest weak point

Self-hosted FFmpeg and Whisper are limited by one machine’s CPU. That is acceptable now. They are already isolated behind queues, so a future managed transcode/transcription service can replace a worker without rewriting the product model.

Scale readiness means knowing which box to replace later—not pretending every box is infinite today.

Say it out loud

Ready-made explanations

Thirty seconds

“It is a private speech-coaching app. React runs the interface, while Laravel owns permissions and business rules. PostgreSQL stores relationships and statuses, and SeaweedFS stores the large media. The browser uploads and streams media directly using short-lived URLs. Slow jobs go through Valkey to separate FFmpeg and Whisper workers, so video can be ready before captions. The key data decision is that a Review is both an invitation/access grant and the folder for one reviewer’s notes.”

For a 10-year-old

“It is a private theater. The speaker owns the show and hands tickets to chosen reviewers. The principal checks every ticket. A ledger remembers who owns what, a warehouse holds the giant videos, and robots prepare the video and type captions. Each reviewer has one folder of sticky notes that pop up at the right time.”

If someone asks, “Why this architecture?”

“Each tool has one job it is good at. The database handles rules and relationships; object storage handles huge seekable files; Laravel handles trust; React handles interaction; queues protect web requests from slow work. The boundaries also give us clean places to test and replace heavy infrastructure later.”

If someone asks, “Is it microservices?”

“No. It is a modular monolith: one Laravel domain and database, with multiple processes and containers. The workers are separated for timeouts, CPU, and dependencies—not because each is its own product.”
