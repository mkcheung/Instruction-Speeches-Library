## Difficulties encountered

1. **A genuine production bug, in code three agents' own tests all passed against.** `AnnotationComposerPanel.tsx`'s `handleComposerEditorReady` did `setComposerSetToPlayhead(fn)` — passing a *function* directly to a `useState` setter, which React interprets as an updater and calls immediately with the previous state rather than storing. This silently invoked `editor.setToPlayhead()` on every mount of the "New note" composer, stamping `start_seconds` to whatever the playhead happened to be (usually `0`) before a user had typed or pressed anything — defeating `useAnnotationEditor.ts`'s entire "nothing is stamped until you act" contract, and specifically the thing the keyboard map's own `Alt+C` test was supposed to prove works. The keyboard-map agent's own vitest-level unit tests (jsdom, no real component mount cycle) could not have caught this; it only surfaced on a live Playwright run against the real merged code. Traced to the exact line by adding `console.log`/stack-trace instrumentation directly to the running dev server — not by reading the diff and guessing — in under 20 minutes. Fixed with the standard React escape hatch (`setComposerSetToPlayhead(() => fn)`), all instrumentation removed before merge.
2. **The `label-content-name-mismatch` root cause took two attempts, and the wrong first hypothesis would have been easy to ship unverified.** The plausible-sounding theory (a viewport-breakpoint `hidden`/`sm:inline` class hiding the visible name at Axe's scan width) turned out to be correct about the *symptom* but required a second, different fix once the agent actually tested removing `aria-label` alone at a real 375px mobile viewport and found it introduced a *new*, more severe critical `button-name` violation — zero accessible name at all below the breakpoint. Caught only by testing the fix at more than one viewport, not by the original hypothesis sounding right.
3. **Docker Desktop and the host-run Vite dev server both went down mid-run, silently stalling a backgrounded agent with no way to signal it.** The keyboard-map agent sat blocked on infrastructure, not its own logic, for several minutes before I diagnosed it from the outside (checking `docker info`, finding the daemon unreachable) and restarted both. The agent itself had no path to report this or resume once unblocked; I finished its remaining validation directly.
4. **My own mistake, caught before it shipped:** Phase 0's baseline was first written to `artifacts/accessibility-baseline/`, matching this repo's existing `whisper-smoke/` naming convention — without accounting for the fact that `artifacts/.gitignore` excludes everything under that directory from version control by explicit design ("Never committed"). This would have silently defeated §7.7.4's one hard requirement (commit the baseline before any fix lands). Caught by checking `git status --short artifacts/` after the capture and noticing the new directory wasn't appearing as untracked; relocated to a new, committed, repo-root `accessibility-baseline/` directory instead.
5. **The permanent `accessibility.spec.ts`'s `login()` helper used Playwright's default `waitUntil: 'load'` instead of this repo's house convention, `'domcontentloaded'`** — every other spec in the suite (including this same file's own three screen-navigation calls) uses the latter. `'load'` waits for every sub-resource, which made this one function far more exposed to the documented Vite dev-server stall than the rest of the suite, and it failed twice in a row with a blank-page screenshot before the inconsistency was noticed and fixed to match house convention.
6. **The Vite dev-server stall (documented in project memory as lasting 60s–4min under host load) recurred repeatedly throughout this session's many live verification runs**, each time as a `page.goto: Test ended` or blank-page timeout on an otherwise-correct test — confirmed each time by immediately re-running the same test alone, which passed in 1–20s. This is pre-existing infrastructure flakiness, not something this step introduced or fixed.

## Mistakes made

1. **Trusted a plausible root-cause hypothesis before testing it at more than one viewport** (Difficulty #2) — worth carrying forward as a standing rule for any accessibility fix touching responsive/viewport-dependent markup: verify the fix at the viewport the automated scan actually used *and* at a realistic alternate viewport, not just the one that reproduced the original finding.
2. **Wrote the Phase 0 baseline output path without checking the target directory's own gitignore rules first** (Difficulty #4). The specific rule worth keeping: before committing anything new to a directory this repo already uses for similar-sounding output (here, `artifacts/`'s existing `whisper-smoke/` precedent), check what that directory's own `.gitignore` actually says — a plausible naming-convention match is not the same as a committable location.
3. **A `/code-review high --fix` pass, run by the user after this retrospective's own verification was substantially complete, found one more real bug this session's own three validation rounds had all missed:** `isTypingContext()` in `useKeyboardShortcuts.ts` never excluded a focused `<select>` element, so a reviewer type-ahead-selecting an annotation's "Kind" dropdown with the letter `c` also fired the global `C`-stamp shortcut, silently overwriting `start_seconds`; the same gap also made `Space` block the dropdown's native open behavior instead of toggling it. Fixed by adding `SELECT` to the same exclusion list `<textarea>` already uses, confirmed sufficient because `isTypingContext` gates `Space` too before any key-specific branch runs. A permanent regression test was added for it. Worth noting as a reminder that "two `/code-review` passes already ran" is not the same claim as "nothing more is findable" — a third, differently-angled pass still found something real.

## Package/tooling surprises

- `@base-ui/react` 1.7.0's `TabsPanel` unmounts an inactive panel by default (`keepMounted` defaults `false`) — not something assumed from the package's docs, but read directly from the installed `node_modules` source (`TabsPanel.js:36,100-102`) before relying on it, since this was the load-bearing fact behind §7.7.1's entire reframing of what "always available" meant in practice.
- React's `useState` setter treats a bare function argument as an updater and invokes it immediately with the previous state, rather than storing the function as the new state — a well-known but easy-to-miss React gotcha (Difficulty #1 above), not specific to this codebase, but this is the first place in this project's history it's bitten real shipped code.
- Playwright's own `Test timeout of 30000ms exceeded` and `page.goto: Test ended` errors both present identically for "the dev server genuinely stalled" and would present identically for a real hang in application code — the only reliable way to distinguish them, used repeatedly this session, is re-running the exact same test alone immediately afterward.
